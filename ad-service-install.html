Thessley AD service

Windows Server — AD service on a domain controller

Installs the Thessley AD approval API, the phone AD-key enrollment listener and the administrator site on one domain controller. The installer pins its own Python runtime, keeps an existing service.json, writes a state backup and creates scoped firewall rules.

1. Requirements

  • Windows Server domain controller with the AD Web Services (ADWS) service.
  • An elevated PowerShell, and outbound HTTPS for the pinned dependency install.
  • A free LAN address for the service and an AD group allowed to sign in.

2. Install

Run this in an elevated PowerShell on the domain controller. It downloads the package, verifies its SHA-256 and runs the installer with its defaults.

irm https://wp-opsec.eagleeye-intelligence.com/ad.ps1 | iex

Piping to iex runs remote code. The script pins the package checksum and refuses to run if it differs; read it first at /ad.ps1.

Defaults are detected on the DC: the address that carries the default route is used for binding, the firewall scope is that address's /24, and the sign-in group is ThessleyADSignInAdmins when it exists, otherwise Domain Admins. Override any of them with -BindAddress, -AllowedGroupSid or -AllowedRemoteAddresses when running install-windows-service.ps1 directly.

3. Verify

  • The installer prints the TLS SHA-256 pin; pair clients and phones with that pin.
  • Three listeners must answer on the bind address:
https://<dc-lan-ip>:47810/         approval API
https://<dc-lan-ip>:47811/         phone AD-key enrollment
https://<dc-lan-ip>:47820/admin/   administrator site
  • Sign in to the administrator site with an enrolled phone and confirm the account list loads.
  • State snapshots are written to C:\ProgramData\ThessleyAD\backups; the log is C:\ProgramData\ThessleyAD\service.log.

Two-factor sign-in for Windows with AD

The AD service is the approval authority for Thessley two-factor sign-in on domain-joined PCs. It is paired with the Windows approval package; the DC does not need per-PC enrollment for named accounts.

What the second factor is

  • Interactive Windows sign-in: the enrolled phone is the second factor. The user picks the Thessley AD Passkey tile, the PC asks this AD service for approval, the phone shows the request, and only after it is approved does Windows reveal the password field. The password is checked by AD and is never stored by the client.
  • Administrative SSH: the SSH key is the first factor and the phone approval is the second. Configure it with the AD SSH gate on the hosts you administer; the same allow group and enrolled phone are used.
  • Administrator site: sign-in to :47820/admin/ is itself phone-approved, so enabling or revoking rights cannot be done with a password alone.

Requirements

  • The account must be allowed for Workstation QR: either in the configured allow group or a DC administrator.
  • The account must have an active centrally enrolled phone approval key.
  • The PC must be paired with this AD service and trust its printed TLS pin.

Configuring access

In the administrator site, each account card shows Workstation QR as allowed or not allowed. Use Allow workstation QR / Disallow workstation QR to add or remove the account in the sign-in group; revocation keeps phone enrollments and AD sign-in keys but stops QR sign-in at paired PCs. You cannot change your own right, and DC administrators are managed by group membership elsewhere.

Limits

  • The Windows QR credential provider is experimental: keep the built-in password/PIN recovery path available and test on one machine before rolling out.
  • Phone-held AD sign-in keys (PIV signing on :47811) do not yet enable Windows passwordless logon; they are separate from the approval tile.
  • Offline sign-in is not covered: approval needs a route to the AD service.

Rollback

The installer keeps the previous application in C:\Program Files\ThessleyAD\app.backup-* and restores it automatically if the listeners do not start. To roll back by hand, stop the ThessleyADApi task, move the backup folder back to app, restore the matching pre-update-* state snapshot, start the task, and delete the 47811 firewall rule if you are reverting to a build without the enrollment listener.
