Thessley computer installation

Windows 11 Pro office client

OpenSSH with key sign-in and the Office PC Users logon model, in three steps.

All downloads · Windows agent · Linux · AD service

Before you start

  • Windows 11 Pro, Enterprise or Education, installed and joined to the domain — or a local account on a one-user workstation (use .\Martin).
  • An elevated PowerShell window, and the user signed in once (so the profile exists).
  • The public key of the user, or a URL that serves it.
  • A local break-glass administrator you can still use if the domain is unreachable.

Guided install

0. Check the machine, and join the domain if needed

One command reports admin rights, domain state, DNS, the signed-in user and whether OpenSSH is there:

& ([scriptblock]::Create((irm https://wp-opsec.eagleeye-intelligence.com/wp-content/uploads/thessley-downloads/windows-office-client.ps1))) -Check

If it is not joined yet, let the same script do it. It resolves the domain first, so a DNS problem is reported instead of a failed join:

& ([scriptblock]::Create((irm https://wp-opsec.eagleeye-intelligence.com/wp-content/uploads/thessley-downloads/windows-office-client.ps1))) -Domain lab.thessley.test

It prompts for an account that may join, reboots, and prints what to run next.

1. Install OpenSSH Server

Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
if (-not (Get-NetFirewallRule -Name OpenSSH-Server-In-TCP -ErrorAction SilentlyContinue)) {
  New-NetFirewallRule -Name OpenSSH-Server-In-TCP `
    -DisplayName "OpenSSH Server (sshd)" -Enabled True -Direction Inbound `
    -Protocol TCP -Action Allow -LocalPort 22
}

Windows normally creates the firewall rule itself; the guard just keeps a rerun quiet.

2. Add the key

& ([scriptblock]::Create((irm https://wp-opsec.eagleeye-intelligence.com/wp-content/uploads/thessley-downloads/windows-office-client.ps1))) -SshOnly

It uses the user signed in at this PC (Enter accepts), adds the key with the right ACLs, sets PubkeyAuthentication yes, turns password sign-in off and restarts sshd. The key comes from the clipboard, a .pub file, or a URL such as https://github.com/alice.keys.

Test it from another computer before step 3: ssh -i <key> <user>@<host>.

3. The office logon model

& ([scriptblock]::Create((irm https://wp-opsec.eagleeye-intelligence.com/wp-content/uploads/thessley-downloads/windows-office-client.ps1))) -LogonModelOnly

Creates the local group Office PC Users and allows only Administrators and that group to sign in locally, over Remote Desktop and over the network. Keep the console open while it runs.

Steps 2 and 3 in one command, after step 1: irm https://wp-opsec.eagleeye-intelligence.com/wp-content/uploads/thessley-downloads/windows-office-client.ps1 | iex

Verify

  • Sign in at the console and over RDP as the user: both work, and it is an ordinary user.
  • ssh -i <key> <user>@<host> opens a shell.
  • An account in neither Administrators nor Office PC Users is refused by all three.
Options
  • -User 'CONTOSO\alice' — a different user than the one signed in.
  • -KeyUrl https://github.com/alice.keys — where to fetch the key.
  • -KeepPasswordAuth — keep password sign-in alongside the key.
  • -Group 'Office PC Users' — a different local group.
  • -Rollback — restore the saved sshd_config and logon rights.

Backups go to C:\ProgramData\ThessleyOffice\backup-<timestamp>. Checksums: SHA256SUMS.txt.

If it goes wrong
  • SSH works on the PC but not from another computer — the firewall rule is only enabled for some profiles: Set-NetFirewallRule -Name OpenSSH-Server-In-TCP -Enabled True -Profile Any.
  • “Permission denied (publickey)” — wrong key file for the account (.ssh\authorized_keys vs administrators_authorized_keys), file ACLs, or SeNetworkLogonRight.
  • “Cannot resolve” the account — not domain-joined or no DC reachable; use .\localuser for a local account.
  • Passkey tile says “Approval failed or expired” — the AD service is down: sc.exe query ThessleyADApi on the DC (“1060” = not installed, see AD service).
  • Domain trust failed — sign in locally, Reset-ComputerMachinePassword -Server DC1 -Credential (Get-Credential CONTOSO\Administrator), reboot.
Raw commands (no installer)

Key for a standard user, run as that user:

$dir = Join-Path $env:USERPROFILE '.ssh'
New-Item -ItemType Directory -Force $dir | Out-Null
Add-Content "$dir\authorized_keys" 'ssh-ed25519 AAAA... user@host'
icacls $dir /inheritance:r /grant "$($env:USERNAME):(OI)(CI)F" /grant "SYSTEM:(OI)(CI)F"
icacls "$dir\authorized_keys" /inheritance:r /grant "$($env:USERNAME):F" /grant "SYSTEM:F"

Administrator keys go to C:\ProgramData\ssh\administrators_authorized_keys instead (ACL: Administrators and SYSTEM). Then in C:\ProgramData\ssh\sshd_config:

PubkeyAuthentication yes
PasswordAuthentication no

Logon rights, with C:\Windows\Temp\office-rights.inf:

[Unicode]
Unicode=yes
[Version]
signature="$CHICAGO$"
Revision=1
[Privilege Rights]
SeInteractiveLogonRight = *S-1-5-32-544,Office PC Users
SeRemoteInteractiveLogonRight = *S-1-5-32-544,Office PC Users
SeNetworkLogonRight = *S-1-5-32-544,Office PC Users
secedit /export /cfg C:\Windows\Temp\secpol-before.inf
secedit /configure /db C:\Windows\Temp\secedit.sdb /cfg C:\Windows\Temp\office-rights.inf /areas USER_RIGHTS
