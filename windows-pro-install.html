Thessley computer installation

Windows 11 Pro office client

A clean Pro install for the office logon test: UEFI with TPM 2.0, domain join, OpenSSH with key sign-in, and the Office PC Users logon model.

What you need

Windows 11 Pro, Enterprise or Education

Windows Home cannot join a domain and cannot host Remote Desktop, so it cannot run this model at all. Use Pro or higher.

Plan for 4 GB RAM, 2 vCPUs and 60 GB of disk. Keep UEFI and a TPM 2.0 device: the passkey and PIV work later needs the TPM, and Windows 11 Setup expects it.

The installation media

Download the Windows 11 ISO from Microsoft’s software download page and check its SHA-256 against the value Microsoft publishes for that build. A volume-licence ISO from your own agreement works the same way.

On this lab host the ISO is already installed as /var/lib/libvirt/images/windows-pro-install.iso (about 7.2 GB). Reuse it instead of downloading another copy, and keep the matching virtio driver ISO (virtio-tools.iso) next to it for the disk driver and guest tools.

Licensing. This guide only installs the operating system. Activation is your responsibility: retail, volume or evaluation media must match the licence you hold, and the lab network should stay isolated from production while the weak test passwords from the lab notes are in use.

Create the virtual machine

Run this on the lab host. Adjust the name, disk path and memory for your host; the shape (q35, UEFI, TPM 2.0, virtio disk and network) is what matters.

sudo virt-install \
  --name office-client \
  --osinfo win11 \
  --memory 4096 --vcpus 2 \
  --machine q35 --boot uefi,secure=on \
  --tpm backend.type=emulator,backend.version=2.0 \
  --disk path=/var/lib/libvirt/images/office-client.qcow2,size=60,format=qcow2,bus=virtio \
  --cdrom /var/lib/libvirt/images/windows-pro-install.iso \
  --disk path=/var/lib/libvirt/images/virtio-tools.iso,device=cdrom \
  --network network=default,model=virtio \
  --graphics spice,listen=127.0.0.1 \
  --video qxl \
  --noautoconsole

If libvirt rejects --boot uefi,secure=on, install the OVMF Secure Boot firmware (ovmf package) or drop ,secure=on; the TPM still works without Secure Boot, but Windows 11 Setup may ask you to acknowledge the requirement.

Install Windows

  1. Connect to the console (virt-viewer -c qemu:///system office-client), boot the ISO, and choose Custom: Install Windows only.
  2. If Setup shows no disk, choose Load driver and pick amd64\w11\viostor.inf (or vioscsi.inf) from the virtio ISO. The disk then appears.
  3. Select Windows 11 Pro and install to the whole disk.
  4. At the network/account step, create a local break-glass administrator rather than tying the machine to a Microsoft account. On current builds press Shift+F10 and run start ms-cxh:localonly; on older builds you can use oobe\bypassnro. The break-glass account is what gets you back in if domain sign-in or a logon policy goes wrong.
  5. Install the guest tools from the virtio ISO (virtio-win-guest-tools.exe) for display, clipboard and ballooning, then reboot.
  6. Run Windows Update, set the time zone, and confirm the clock is correct. Phone approvals are time-sensitive.
Set-TimeZone -Id "W. Europe Standard Time"
w32tm /resync

Join the domain

Name the computer before joining, then use a domain account that may join workstations. The restart is required.

Rename-Computer -NewName OFFICE1 -Restart
Add-Computer -DomainName lab.thessley.test -Credential (Get-Credential THESSLEYLAB\Administrator) -Restart

After the restart, sign in once with the domain account you will use for the test so its profile exists, then confirm the secure channel:

Test-ComputerSecureChannel -Verbose

Install OpenSSH Server

Windows ships OpenSSH as a capability. Install the server, start it at boot, and open only TCP 22.

Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
New-NetFirewallRule -Name OpenSSH-Server-In-TCP -DisplayName "OpenSSH Server (sshd)" `
  -Enabled True -Direction Inbound -Protocol TCP -Action Allow -LocalPort 22

Add the public key

For a standard (non-administrator) account the key goes in that user’s own profile. Run this as that user after their first sign-in:

$key = 'ssh-ed25519 AAAA... your-name@your-host'
$dir = Join-Path $env:USERPROFILE '.ssh'
New-Item -ItemType Directory -Force $dir | Out-Null
Add-Content -Path (Join-Path $dir 'authorized_keys') -Value $key
icacls $dir /inheritance:r /grant "$($env:USERNAME):(OI)(CI)F" /grant "SYSTEM:(OI)(CI)F"
icacls (Join-Path $dir 'authorized_keys') /inheritance:r /grant "$($env:USERNAME):F" /grant "SYSTEM:F"

The default C:\ProgramData\ssh\sshd_config ends with a Match Group administrators block that redirects administrator keys to a shared file. Either leave it and put the key in C:\ProgramData\ssh\administrators_authorized_keys (ACL: Administrators and SYSTEM only), or remove that block if every account uses its own profile:

icacls C:\ProgramData\ssh\administrators_authorized_keys /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"

Turn off password sign-in

PubkeyAuthentication yes
PasswordAuthentication no

Put those two lines in C:\ProgramData\ssh\sshd_config, then restart and test from another computer:

Restart-Service sshd
ssh -i ~/.ssh/thessley-vm-debug martin@office1

The office logon model

The goal: only administrators and members of a local Office PC Users group may sign in at the PC, over Remote Desktop, and over the network. Everything else is refused, including SSH.

New-LocalGroup -Name "Office PC Users" -Description "May sign in at this PC"
Add-LocalGroupMember -Group "Office PC Users" -Member "THESSLEYLAB\martin"

Keep a way back in. Before changing logon rights, export the current policy and keep a local administrator plus console access. If the only account allowed to sign in is a domain account and the domain is unreachable, the PC is locked out.

secedit /export /cfg C:\Windows\Temp\secpol-before.inf

Create C:\Windows\Temp\office-rights.inf with these rights. *S-1-5-32-544 is the local Administrators group; the group name is the local group created above.

[Unicode]
Unicode=yes
[Version]
signature="$CHICAGO$"
Revision=1
[Privilege Rights]
SeInteractiveLogonRight = *S-1-5-32-544,Office PC Users
SeRemoteInteractiveLogonRight = *S-1-5-32-544,Office PC Users
SeNetworkLogonRight = *S-1-5-32-544,Office PC Users
secedit /configure /db C:\Windows\Temp\secedit.sdb /cfg C:\Windows\Temp\office-rights.inf /areas USER_RIGHTS
gpupdate /force

Do not leave out SeNetworkLogonRight. SSH signs in as a network logon. With only the interactive and Remote Desktop rights, a correct key is still answered with Permission denied (publickey) — the exact failure this lab hit. The safe set is all three rights for the same two principals.

Roll back

secedit /configure /db C:\Windows\Temp\secedit.sdb /cfg C:\Windows\Temp\secpol-before.inf /areas USER_RIGHTS

Verify

  1. Sign in at the console and over Remote Desktop as THESSLEYLAB\martin: both must work, and the session must be an ordinary user, not an administrator.
  2. From another computer: ssh -i <key> martin@office1 must open a shell with the same standard-user token.
  3. An account that is in neither Administrators nor Office PC Users must be refused for all three.
  4. Reboot and repeat: the rights are local policy and must survive a restart.

If it goes wrong

The passkey tile says “Approval failed or expired”

The computer cannot reach the AD service. Check it on the domain controller: sc.exe query ThessleyADApi. A “1060: the specified service does not exist” answer means the AD service is not installed on that DC (a freshly rebuilt DC has none); install it from the AD service guide before testing passkey sign-in.

SSH answers “Permission denied (publickey)” with a key that works elsewhere

Check, in this order: the key is in the right profile (a domain user needs one sign-in to create it), the Match Group administrators block, the ACLs on .ssh and authorized_keys, and SeNetworkLogonRight for the account’s groups.

“The trust relationship between this workstation and the primary domain failed”

Sign in with the local break-glass administrator and reset the machine password, then reboot:

Reset-ComputerMachinePassword -Server THESSLEY-DC1 -Credential (Get-Credential THESSLEYLAB\Administrator)

SSH is slow or times out right after boot

sshd resolves the domain account at logon. Until DNS and the domain controller answer, the banner can take seconds or the attempt can time out. Wait for the DC, then retry before changing anything.
